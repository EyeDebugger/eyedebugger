    Why eyedbg

    Agents guess. Debuggers know.

    When a fix based on reading the code fails once or twice, the fastest way forward is to look at what the program really does. eyedbg gives your agent a real debugger it drives from the shell — and gives you a seat in the same session.

    01

    Evidence, not hypotheses

    Stop where the bug happens, read the locals that changed, evaluate an expression in the frame that matters. The agent works from the values the program really has at runtime, not from what the code suggests.

    02

    Made for how agents work

    One stateless command per step, each answering with the full picture. Output is budgeted to fit a context window, JSON and error codes are stable, and the built-in help is the documentation. No MCP server to install or configure.

    03

    A session you can share

    Existing agent debuggers are MCP servers or bound to an IDE, and none lets an agent and a human both drive one session. With eyedbg, a daemon owns the session and every client joins it: the agent's CLI, your VS Code, any DAP client.

    How it works

    One daemon owns the session. Everyone else is a client.

    The eyedbg CLI is stateless: each command is a short call to eyedbgd, a per-user daemon that holds your debug sessions and drives a proven Debug Adapter Protocol (DAP) debugger for each language. Your editor connects to the same daemon, so the agent and you always see the same program state.

    Stateless CLI

    Each command is one short-lived process: it connects, does one thing and exits. Agent harnesses that run every command in a fresh shell just work.

    A daemon you never manage

    The first command starts eyedbgd; it serves all your sessions and exits after 30 idle minutes. An adapter crash ends only its own session.

    Local and authenticated

    A Unix socket in a directory only you can enter, and a fresh random token checked on every connection. No TCP listener, even for editors.

    Proven debuggers

    eyedbg adds no engine of its own: it drives DAP adapters, each described by a JSON manifest that says how to install, find and launch it.

    The agent loop

    From bug to cause in five commands

    A wrong order total, found the way your agent would find it. Every execution command answers with where the program stopped, the source around it and the locals that changed, so there's never a follow-up call just to see where it is.

    Safe by default

    An expression that could change the program is refused, with a stable code and a hint. --allow-side-effects runs it: that takes the control lease and is recorded in the session's events.

    Terminal

    eyedbg stop ends the session and the program, or detaches from a program you attached to. The daemon goes away by itself once it's idle.

    Features

    A full debugger, shaped for agents

    Launch and attach, breakpoints of every kind, stepping, threads, stacks, variables, eval and set — with output an LLM can read in one pass and a human can trust.

    Every step answers with the stop

    continue, next, step-in, step-out and run-until wait until the program stops, exits or times out (30 s by default), then print the reason, the location, the source around it and the locals that changed. A timeout isn't an error: the program keeps running and eyedbg wait picks it up.

    Terminal
    $ eyedbg next
session s-7f3k (dotnet, netcoredbg) stopped: step, thread 4242
  at Shop.Orders.Total() Orders.cs:19
    18 |         total += order.Price * order.Quantity;
  > 19 |     }
    20 |     return total;
  changed since the previous stop:
    total: decimal = 42.50  (was 127.50)

    Anchors, not line numbers

    Orders.cs@"var total =" resolves to the one line that holds the text, and reports the line it found. The agent sets breakpoints by what the code says, not by numbers that drift with every edit.

    File:LINEFile@"text"func:Name

    Conditions, hit counts, logpoints

    Stop only when it matters, or print instead of stopping. eyedbg runs hit counts and logpoints itself, so they behave the same on every adapter.

    --if 'i == 3'--hit '>=3'--log 'i={i}'

    Output that fits a context window

    Variables are cut to --budget tokens (2,000 by default), and every cut says how to see the rest, like eyedbg vars --expand orders.

    budget2,000 tokens

    Eval that won't surprise you

    Method calls, assignments, new and ++ are refused as SIDE_EFFECTS unless you pass --allow-side-effects, which needs the control lease and is logged.

    Exception stops

    eyedbg bp exceptions uncaught (or all) stops where an exception is thrown; the stop shows its type, message, stack and inner exception, and $exception evaluates it.

    Attach, or debug a test

    eyedbg attach dotnet --pid 4321 joins a running process of yours. eyedbg test dotnet Adds runs dotnet test attached to the test host, so breakpoints in the tests and the code they call hit; Go runs tests with --opt mode=test.

    A log of who did what

    eyedbg events --since 12 --wait long-polls the session's event log: stops, steps, breakpoints, lease changes and output, from every client. A late joiner catches up in one call.

    Machine-readable when you want it

    --json on any command returns output with a "schema" version. Errors carry a stable code, a message and a hint to follow, and exit codes group them: 1 usage, 2 state, 3 setup, 4 adapter.

    eyedbg continue --json
    {
  "schema": 1,
  "error": {
    "code": "LEASE_HELD",
    "message": "the lease of session s-7f3k is held by human:alex (policy human-priority)",
    "hint": "ask human:alex to run 'eyedbg lease grant agent'; 'eyedbg events --wait --kind lease' waits for a change"
  }
}

    Nothing to babysit

    No server to start, no port to pick. The daemon starts with the first command, one per user, and cleans up after itself. eyedbg daemon status shows what it's doing.

    Co-debugging

    One session. Two drivers.

    Join the agent's live session from VS Code, or start one with F5 and let the agent join you. You see where it stopped, its breakpoints and everything it does; a control lease decides who drives.

    • A control lease, not a free-for-all

      Exactly one client holds execution control: continue, step, pause, set and side-effecting eval. Everyone else can read state, set their own breakpoints and ask for control.

    • Breakpoints keep their owners

      The agent's breakpoints show in your editor with whose they are and what they do (⬥ agent · if total > 3). Removing one only hides it for you; Copy as My Breakpoint makes it yours.

    • Follow the agent, keep your focus

      When the agent's step stops, VS Code shows the line without taking your keyboard focus. The Activity and Clients views list what each client did, who is connected and who has control.

    • Join when an agent starts

      When an agent starts debugging a program in your workspace, VS Code offers to join — once per session, and never without your click.

    • Any DAP client

      eyedbg dap speaks standard DAP on stdio and joins a running session under the same rules — for nvim-dap, scripts or another editor.

    Built for agents

    The help is the interface

    No schema to register and no server to run. An agent learns eyedbg the way it learns any command-line tool — by reading its help — and every page of that help is written, tested and kept in sync for exactly that reader.

    Every command documents itself

    What it does, when to use it, how long it blocks, its effect on the program, its output and its exit codes, with real examples. eyedbg help --all prints the whole tree in one read; --json returns it as data.

    Shell
    eyedbg help --all           # every command, one read
eyedbg help run-until       # one command
eyedbg help --all --json    # the same, as data

    A skill in one command

    eyedbg skill install writes SKILL.md — when to reach for the debugger, the standard loop, budgets, sharing etiquette and "always stop" — into Claude Code's skills folder. --dir targets another agent's.

    Terminal

restart your agent (or start a new session) to load it

    Errors that say what to do next

    Every error has a stable code and a hint, so the agent recovers instead of guessing. Here, a human holds control, and the hint says how to ask for it.

    Terminal
    $ eyedbg continue
eyedbg: the lease of session s-7f3k is held by human:alex (policy human-priority) [LEASE_HELD]
hint: ask human:alex to run 'eyedbg lease grant agent'; 'eyedbg events --wait --kind lease' waits for a change

    Exit codes to branch on

    Scripts and agents can tell a usage mistake from a busy session or a missing adapter without parsing text.

    ExitMeans
    0Success — including a wait that timed out (the output says so)
    1Usage: a bad request, SIDE_EFFECTS, an anchor not found
    2State: no session, not stopped, LEASE_HELD, not the owner
    3Setup: adapter not installed, build or attach failed — run the hint
    4The adapter or side helper refused or can't do it
    Security and privacy

    A debugger sees everything. It stays on your machine.

    Debug sessions hold secrets: tokens in variables, customer data in memory. eyedbg is built to keep them yours.

    Local only, no telemetry

    The daemon listens on a Unix socket in a private directory — never TCP — and checks a fresh random token on every connection. eyedbg has no telemetry — it even turns off the .NET CLI's for the builds it runs — and goes online only to download adapters you install.

    Your processes only

    attach and eyedbg dotnet check that a process is yours before anything runs, and show it as pid N (name) — never by its command line.

    Read-only eval by default

    Expressions that would change the program need --allow-side-effects, which takes the control lease and is recorded — so a stray eval can't quietly change state someone else is looking at.

    Pinned, verified adapters

    Adapter downloads are https, size-capped and SHA-256-checked before extraction, through a staging directory that refuses escaping paths. Manifests are never read from a project.

    Private dumps and traces

    Written under fresh random names in a directory only you can read, never overwritten, pruned after 7 days. Session recordings keep control events only — no output or values.

    Never vsdbg

    Microsoft's .NET debugger is licensed for Microsoft's tools only. eyedbg never downloads, detects or runs it; .NET debugging uses the MIT-licensed netcoredbg and SharpDbg.

    Install

    Up and running in four steps

    Once per machine. After that, your agent starts sessions on its own and you join them when you like.

    Get eyedbg

    Download the archive for your platform from the latest release: eyedbg, eyedbgd and the .NET side helper. Keep them together on your PATH, and check the archive was built by the project's release workflow. With Go 1.26 or later, go install works too (without the .NET helper).

    Verify a download
    gh attestation verify eyedebugger_X.Y.Z_linux_amd64.tar.gz -R EyeDebugger/eyedebugger
    Or with Go
    go install github.com/eyedebugger/eyedebugger/cmd/eyedbg@latest github.com/eyedebugger/eyedebugger/cmd/eyedbgd@latest

    Install a debug adapter

    Pinned and checksum-verified. Name an adapter or a language; C, C++ and Rust use the lldb-dap on your PATH. doctor checks what you have.

    Shell
    eyedbg adapters install netcoredbg   # or: python, delve, sharpdbg
eyedbg adapters doctor

    Teach your agent

    Installs the skill for Claude Code. For another agent, use --dir with its skills folder, or point it at eyedbg help --all.

    Shell
    eyedbg skill install

    Join from VS Code

    Install the EyeDebugger extension — from the VSIX attached to each release, or from the VS Code Marketplace and Open VSX. It finds eyedbg on your PATH, or set eyedbg.path.

    Shell
    code --install-extension eyedebugger_X.Y.Z_vscode.vsix
    FAQ

    Questions, answered

    Is eyedbg an MCP server?

    No. The CLI is the interface: any agent that can run a shell command can use it, and eyedbg help --all teaches it the whole tool in one read. There's nothing to register and nothing to keep running — the daemon starts by itself.

    Which agents does it work with?

    Any agent with a shell: Claude Code, Codex and others. eyedbg skill install installs SKILL.md for Claude Code; for other agents, install it with --dir, print it with eyedbg skill print, or let the agent read eyedbg help --all.

    Can an agent and I really drive the same session?

    Yes. The daemon owns the session; the agent's CLI and your editor are both clients of it. One control lease decides who may run, step or pause; everyone else can read state, set their own breakpoints and ask for control. Breakpoints on the same line are merged and keep their owners.

    Will the agent take control away from me?

    Under the default free policy, whoever acts takes control. Switch to human-priority — VS Code offers it when you take over — and agents have to ask: a human can always take control from an agent, never the other way round. The agent skill tells agents never to force the lease over a human.

    Why not Microsoft's vsdbg for .NET?

    Its license restricts it to Microsoft's own tools. eyedbg uses netcoredbg (Samsung, MIT) by default and the opt-in SharpDbg (MIT), and never downloads, detects or launches vsdbg. The result is a free VS Code .NET debugging experience without the license question.

    Is eval safe to run on my program?

    It's read-only by intent: expressions that visibly change the program — method calls, assignments, new, ++ — are refused unless you pass --allow-side-effects. The check is best-effort: property getters still run code, as they would in any debugger.

    Does anything leave my machine?

    No. The daemon has no network listener and eyedbg has no telemetry. The only downloads are the adapters you ask for, pinned and checksum-verified.

    What does it run on?

    Linux, macOS and Windows, on x64 and arm64. On Intel Macs and Windows on Arm, .NET debugging uses SharpDbg, since netcoredbg has no build there.

    What does it cost?

    Nothing. EyeDebugger is open source under the Apache-2.0 license, and contributions are welcome.
